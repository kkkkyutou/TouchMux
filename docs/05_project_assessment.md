# 项目评估与下一阶段建议

## 1. 项目是什么

TouchMux 不是传统的“SSH 网页客户端”，而是一个面向手机浏览器的远程工作台。它通过网页去管理 `tmux` 会话、`codex` CLI 和受控文件区，并支持两类部署方式：

- `single`
  - 单机直连模式
  - 一个 TouchMux 实例管理一台机器
- `hub + node`
  - Hub 作为统一入口
  - 多台 Node 机器负责本地 `tmux`、`codex`、文件系统和 Goal Guard

从当前代码和脚本看，它已经不是概念原型，而是一个可运行的演示级 MVP。单机主链路可用，多机 `hub + node` 第一版也已经落地。

## 2. 当前已实现的功能

### 2.1 会话与终端

- 口令登录后进入移动端工作台
- 创建新的 Codex 会话
- 从历史 Codex session 恢复到新的 `tmux` 会话
- 从历史 Codex session fork 到新的 `tmux` 会话
- 关闭会话与强制停止会话
- 通过 WebSocket 附着到 `tmux` 终端
- 终端窗口尺寸变化后同步 resize
- 会话列表和状态通过事件通道持续推送

### 2.2 多机聚合

- `single / hub / node` 三种运行模式已经在同一后端中实现
- Hub 可以读取静态节点列表
- Hub 可以代理节点的会话创建、关闭、文件操作和 Goal Guard 更新
- Hub 可以代理前端到 Node 的终端 WebSocket 连接
- 前端可以切换目标机器并查看对应会话

### 2.3 文件管理

- 受控根目录列表
- 目录浏览
- 面包屑导航
- 返回上一级
- 文本文件读取与保存
- 创建文件夹
- 创建文件
- 文件改名
- 文件删除
- 文件上传
- 文件下载
- 将文件浏览器同步到当前终端目录

### 2.4 移动端交互

- 默认控制台保持空白，必须显式选择某个会话后才显示终端
- 左侧抽屉集中承载节点切换、会话选择和会话创建
- 会话创建表单支持路径输入
- 会话创建表单支持目录建议
- 常见终端交互提供触控快捷按钮
- 文件管理在移动端以底部抽屉方式呈现
- Goal Guard 面板在抽屉中折叠展示，避免挤占主终端区域

### 2.5 Goal Guard 与辅助能力

- 会话可配置 Goal Guard
- 支持成功关键词判定
- 支持命令校验判定
- 空闲超时后可自动注入续跑提示
- 普通停止会受到 Goal Guard 限制
- 支持强制停止覆盖
- 支持从 `~/.codex/history.jsonl` 导入历史会话索引
- 支持启发式识别常见终端选项并提供点击操作
- 具备基础审计日志
- 具备基础登录限流
- 具备健康检查与配置 schema 接口

## 3. 当前未完成或仍属 MVP 的部分

以下内容从 README、文档和代码实现三方面交叉确认，属于当前明确未完成项。

- 多用户账号体系尚未实现
- 角色权限与权限隔离尚未实现
- 节点自动注册尚未实现
- 节点管理页面尚未实现
- 在网页内维护节点列表尚未实现
- 二进制文件预览尚未实现
- 更完整的网页编辑体验尚未实现
- 大文件处理策略尚未实现
- 终端选项点击仍然是启发式识别，不是完整 TUI 语义解析
- Goal Guard 仍然是规则式判定，不是真正理解任务完成度的语义判定
- 后端重启后的恢复只是部分实现，仍依赖真实 `tmux` 状态
- Docker 目前更像演示骨架，不是完整开箱即用部署
- 安全加固还没有达到生产级

另外，代码里还有几处值得单独标记的“半完成状态”：

- 后端重启后，数据库里的会话状态会和 `tmux` 状态重新对齐，但内存中的最近输出缓冲、选项检测状态不会恢复。
- Hub 模式下的会话聚合依赖定时轮询节点，而不是事件驱动同步。
- `SystemPanel` 组件已经写出，但当前主界面没有真正挂载使用。
- 文档中列出 `GET /api/goal-guard/:sessionId`，但 Hub 分支实际只提供更新与强制停止，前端也主要依赖会话快照携带的 Goal Guard 信息。

## 4. 当前系统架构判断

## 4.1 后端架构

当前后端是一体化 Node.js 服务，核心包括：

- Express HTTP API
- WebSocket 事件通道
- WebSocket 终端通道
- `tmux` 托管与附着
- SQLite 持久化
- Goal Guard 后台轮询
- Hub 到 Node 的 HTTP / WebSocket 代理

优点：

- 结构直接，MVP 推进速度快
- 单机和多机逻辑复用度高
- 部署简单，便于自托管

问题：

- `server.ts` 承担了过多职责，已经接近“总控脚本”式结构
- Hub 路径、本地路径、内部节点路径都在一个入口里，后续扩展会增加维护成本
- 事件同步在单机模式较直接，但 Hub 模式依赖轮询，扩展性一般

## 4.2 前端架构

当前前端是 React 单页应用，页面组织方式比较明确：

- `App.tsx` 负责全局状态、登录态、节点/会话选择、抽屉开合
- `SessionSidebar` 负责节点切换、会话切换、会话创建
- `TerminalPane` 负责 xterm.js 和终端 WebSocket
- `FileBrowser` 负责目录浏览、文件操作与编辑
- `GoalGuardEditor` 负责 Goal Guard 表单

优点：

- 功能分块是清楚的
- 终端、文件、Goal Guard 分别拆成懒加载模块
- 交互方向明显偏移动端，而不是桌面页面简单缩放

问题：

- 认证失效、WebSocket 断连、统一错误恢复这些横切逻辑还比较薄
- 有些组件已经存在，但还没真正接入主链路
- 全局状态还主要靠顶层 `App.tsx` 手工传递，复杂度继续增加后会变难维护

## 5. 可改进的地方

## 5.1 架构层面

### 建议优先级高

- 将后端入口按职责拆分为认证、会话、文件、Goal Guard、Hub、Node、WebSocket 等模块，降低 `server.ts` 的集中复杂度。
- 为 Hub 和 Node 的状态同步补一层更明确的事件机制，减少对 2.5 秒轮询聚合的依赖。
- 把关键运行事件做成更稳定的状态流或持久化事件，减少后端重启后“数据库状态还在，但会话上下文丢失”的问题。
- 明确区分“运行时状态”和“历史记录状态”，例如终端最近输出、Goal Guard 判定历史、自动续跑次数等。

### 建议优先级中

- 为前端增加更清晰的状态层，避免后续所有状态都堆在 `App.tsx`。
- 把目前尚未接入的系统状态面板真正挂进 UI，方便用户排查配置和部署问题。
- 为 API 文档做一次对照清理，修正文档与实际接口的偏差。

## 5.2 交互层面

### 建议优先级高

- 增加 WebSocket 自动重连和断线提示，避免网络抖动后界面静默失效。
- 增加统一的登录失效处理，例如 token 过期后自动跳回登录页或弹出明确提示。
- 用底部抽屉或内嵌表单替代 `window.prompt` / `window.confirm`，改善手机端文件操作体验。
- 为 Goal Guard 保存失败、节点离线、终端附着失败等情况提供更明确的可见反馈。

### 建议优先级中

- 在会话卡片中增加更多状态解释，例如 Goal Guard 是否启用、最近输出时间、是否处于自动续跑状态。
- 文件编辑器增加只读提示、编码/文件类型提示、未保存修改提示的更清晰可视化。
- 会话创建表单可以加入更强的输入校验，例如路径不存在、源 session 不合法等。

## 5.3 安全层面

### 当前已有的基础措施

- 基础口令登录
- 登录限流
- 审计日志
- 文件系统根目录白名单
- Hub / Node 共享密钥鉴权
- 在 `hub` 和 `node` 模式默认拒绝使用默认口令和默认 JWT 密钥启动

### 主要不足

- 当前 token 是自定义 HMAC token，只包含过期时间，没有更完整的会话语义。
- 前端把 token 放在 `localStorage`，对 XSS 风险更敏感。
- CORS 现在是全开放配置，更适合本地自托管，不适合直接面向公网生产环境。
- 健康检查接口暴露的运行信息相对较多，公网暴露时需要更谨慎。
- Hub 到 Node 之间主要靠共享密钥头部鉴权，可信内网场景尚可，但生产级防护还不够。

### 安全改进建议

- 引入更标准的会话模型，至少支持更明确的登录态管理、失效机制和登出语义。
- 考虑改用 `HttpOnly` Cookie 或更稳妥的 access token / refresh token 方案。
- 将 CORS 改为显式白名单。
- 为健康检查区分“探针用最小信息版本”和“登录后详细诊断版本”。
- 为 Hub 和 Node 增加更强的信任机制，例如时间戳签名、请求 nonce，或在部署层强制 TLS / 内网信任边界。
- 在公开部署前补上正式的安全审查，包括会话管理、日志脱敏、反向代理边界和暴露面检查。

## 6. 综合判断

TouchMux 当前已经达到“可运行、可演示、可自用”的阶段，尤其是：

- 单机链路是成立的
- `hub + node` 第一版也是成立的
- 移动端交互方向是明确且有辨识度的

但它依然是一个单用户优先、偏自托管场景的 MVP，而不是生产级远程开发平台。它现在最需要补的，不再是“再多堆几个功能”，而是：

- 让架构更稳
- 让交互更顺
- 让状态恢复更可靠
- 让安全边界更清楚

## 7. 建议的下一阶段目标

下一阶段建议不要同时大铺新功能，而是先围绕“把 MVP 打磨成稳定可持续使用的版本”收敛目标。

建议的阶段目标如下：

### 阶段目标 1

把单机与多机主链路从“可演示”提升到“可稳定日常使用”。

### 阶段目标 2

优先补强横切能力，而不是继续堆新模块：

- 连接稳定性
- 状态恢复
- 统一错误处理
- 认证与安全边界

### 阶段目标 3

在此基础上，再决定是否进入下一轮功能扩展，例如：

- 节点管理 UI
- 多用户与权限
- 更完整的网页编辑器
- 更强的 Goal Guard

## 8. 建议的近期执行顺序

如果要按实际研发节奏推进，我建议近期顺序如下：

1. 修补 WebSocket 重连、登录失效处理、文件操作交互和 Goal Guard 错误反馈。
2. 拆分后端入口结构，收敛 `server.ts` 的职责。
3. 明确并增强会话恢复与运行状态同步机制。
4. 做第一轮安全加固，包括 token、CORS、健康检查暴露面和 Hub / Node 信任边界。
5. 之后再进入节点管理、多用户或更强编辑器等扩展功能。
